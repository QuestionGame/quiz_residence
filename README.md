# Residence Trainer

Тренажер для персоналу ресторану: каталог позицій, квіз-тренажер і робота над помилками
для винної карти, бару, коктейлів і меню кухні. Вхід за логіном і паролем, які видає адміністратор;
адмін-панель для користувачів, позицій меню, результатів працівників і синхронізації з ChoiceQR.

## Як це працює

- **База — Supabase** (Postgres + Auth + Storage). Таблиці: `profiles` (працівники й ролі),
  `menu_items` (позиції всіх розділів; поле `data` — позиція у форматі, який читає квіз),
  `quiz_attempts` (кожна відповідь працівника), `mistake_resets` («Очистити список» у помилках).
- **Права перевіряє база** (Row Level Security у `supabase/migrations`), а не браузер:
  працівник бачить активне меню й лише свої результати; змінювати меню й бачити результати всіх
  може тільки активний адміністратор. Заблокований працівник втрачає доступ одразу, навіть із відкритою сесією.
- **Вхід:** логін + пароль від адміністратора (у Supabase Auth логін зберігається як
  `<логін>@staff.residence.local`). Реєстрація вимкнена. Акаунти створює й змінює лише `api/admin-users.js`
  із service-role ключем, який є тільки на сервері.
- **Мій профіль** (`profile.html`, посилання в панелі облікового запису): кожен може змінити своє ім’я
  й прізвище та пароль (з підтвердженням поточного; після зміни інші пристрої виходять із акаунта).
  База дозволяє користувачу оновлювати лише колонку `full_name` власного рядка — роль, логін і
  блокування акаунта змінює тільки адміністратор. Спеціальний доступ активується, якщо ввести
  код активації після символу `\` у полі «Ім’я» й натиснути «Зберегти». Сервер перевіряє код і
  прибирає його з імені до збереження; після успіху поле показує лише ім’я. Код не вбудований
  у фронтенд і не зберігається в профілі. Адміністратор може вимкнути доступ через адмін-панель.
- **Ключі:** у браузері (`assets/js/config.js`) лише URL і publishable key — вони публічні за задумом.
  `SUPABASE_SERVICE_ROLE_KEY` обходить усі права доступу: він має бути лише в `.env.local` (локально)
  і в Environment Variables на Vercel. Ніколи не комітьте його й не вставляйте у фронтенд.

## Локальний запуск

Потрібні Node.js 20+ і Docker Desktop.

```bash
npm install
npm run db:start      # локальний Supabase у Docker (вперше качає образи)
```

`db:start` виведе `API_URL` і `SERVICE_ROLE_KEY` — запишіть їх у `.env.local` у корені проєкту:

```
SUPABASE_URL=http://127.0.0.1:54321
SUPABASE_SERVICE_ROLE_KEY=<SERVICE_ROLE_KEY з виводу>
ANSWER_ASSIST_ACTIVATION_CODE=<випадковий секрет щонайменше 32 символи>
```

```bash
npm run seed -- --admin admin --password "<пароль від 8 символів>" --name "Ім’я Прізвище"
npm run dev           # http://127.0.0.1:3000 → вхід під цим адміністратором
```

Сторінки тренажера працюють і через Live Server, але адмін-функції (створення працівників,
синхронізація з ChoiceQR) потребують `npm run dev`, бо виконуються на сервері.
Скинути локальну базу до чистої схеми: `npm run db:reset` (потім знову `npm run seed`).

## Розгортання (Supabase + Vercel)

1. Створіть проєкт на supabase.com. У Authentication → Sign In / Providers вимкніть
   «Allow new users to sign up» (акаунти створює адмін).
2. Застосуйте схему: `npx supabase link --project-ref <ref>`, потім `npx supabase db push`.
3. Заповніть базу: `SUPABASE_URL=… SUPABASE_SERVICE_ROLE_KEY=… npm run seed -- --admin … --password … --name …`.
4. Впишіть URL і publishable key проєкту в `PRODUCTION` у `assets/js/config.js`.
5. На Vercel імпортуйте репозиторій і додайте Environment Variables `SUPABASE_URL`
   і `SUPABASE_SERVICE_ROLE_KEY`. Для активації спеціального доступу також задайте
   `ANSWER_ASSIST_ACTIVATION_CODE` — випадковий секрет щонайменше 32 символи. Щоб активувати
   доступ, користувач дописує `\` і значення секрету після свого імені в полі «Ім’я». Не використовуйте
   приклад із документації як реальний код. Функції з `api/` Vercel підхопить автоматично.

## Адмін-панель (`admin.html`)

Посилання — у панелі облікового запису (кнопка з ініціалами в шапці), видно лише адміністраторам.

- **Результати:** таблиця працівників за 7 / 30 днів або весь час, по всіх розділах чи одному:
  кількість відповідей, точність загалом і по кожному розділу, остання активність. Клік по
  працівнику — позиції, де він найчастіше помиляється, і останні відповіді з деталями
  («обрано Віскі — правильно Джин», «пропущено: пармезан»).
- **Позиції:** список розділу з пошуком; редагування й нові позиції (поля — ті, що потрібні квізу;
  форма не дасть зберегти позицію, на якій квіз зламається); фото (зменшується до 800 px);
  «Показувати працівникам» — приховати позицію без втрати історії відповідей.
- **Користувачі:** новий працівник (логін, ім’я, роль, пароль — можна згенерувати; після створення
  логін і пароль показуються один раз для передачі), зміна імені й ролі, новий пароль, блокування.
  Акаунти не видаляються, лише блокуються. Не можна заблокувати чи понизити себе, і завжди лишається
  хоча б один активний адміністратор.
  «Прихований доступ» (прапорець у вікні «Змінити»): у цього акаунта після «Перевірити відповідь» обрані
  варіанти замінюються правильними, і спроба записується як правильна. Також користувач може активувати
  його зі свого профілю, додавши `\` і серверний `ANSWER_ASSIST_ACTIVATION_CODE` до імені; адміністратор може вимкнути
  доступ у вікні редагування. У списках і результатах прапорець не показується.
- **ChoiceQR:** «Перевірити зміни» показує, що оновиться, «Застосувати» записує нові ціни, порції
  напоїв і фото позицій, прив’язаних до страв ChoiceQR (поле «Назва в ChoiceQR» у позиції).
  Склад, алергени й відповіді квізу синхронізація не змінює. Окремо показуються позиції, яких
  більше немає в ChoiceQR, і нові страви ChoiceQR, яких ще немає в тренажері.

## Меню: звідки дані

Після першого імпорту (`npm run seed`) **джерело правди — база й адмін-панель**. Повторний `npm run seed`
не перезаписує позиції, змінені в адмінці (лише з `--force`).

Скрипти `parse_choiceqr_menu.py` → `build_quiz_data.mjs` збирають `data/*.json` для першого заповнення
(або для нової бази). Що робить `build_quiz_data.mjs`:

1. Читає `data/source/menu_clean.json` (ChoiceQR) і `data/source/residence_menu_full.json` (кухня).
2. **Бар і коктейлі:** додає до позицій ChoiceQR правильні відповіді з таблиць `BAR`, `COCKTAILS`.
3. **Кухня** (`scripts/kitchen.mjs`): склад зі специфікації кухні, групи `components`,
   автоматично визначені алергени, ціна / вага / фото / опис зі страви ChoiceQR (таблиця `CHOICEQR`).
4. Нормалізує дані («450 g» → «450 г», ціни, «б/а» для безалкогольних коктейлів, назви) і записує
   для кожної позиції зв’язок із ChoiceQR (`choiceqr`), який `seed` переносить у `menu_items.choiceqr_name`.
5. Завантажує відсутні фото в `assets/img/<розділ>/`.

## Алергени — обов'язково перевірити з кухнею

У специфікації кухні немає поля з алергенами, тому вони **визначаються автоматично** за складом
страви (14 основних алергенів ЄС). Скрипт шукає в інгредієнтах ключові слова (`ALLERGEN_RULES`
у `scripts/kitchen.mjs`) і додає склад базових соусів зі специфікації: Цезар (анчоуси, жовток,
гірчиця, соєвий соус), Песто (**арахіс**, пармезан), Хумус (тахіні), Демігляс (селера, вино),
Соус 7 перців, картопляне пюре (вершкове масло). Для кожного алергену зберігається, яке слово
його викликало — це видно в розборі відповіді квізу.

Правила свідомо обережні (краще зайве попередження, ніж пропущене): глютен ставиться для соєвого
соусу, теріякі, понзу, унагі, хойсін; яйця — для заварного крему; молоко — для будь-якого «масла»
(крім рослинного).

Що варто звірити в першу чергу:
- **Склад невідомий:** соус кімчі, блек пеппер, вишневий і журавлинний соуси, кукурудзяні
  пластівці в паніровці Shrimp-кейків, тісто штруделя й сирників (яйця?).
- Брауні (карамельний чізкейк) позначено як глютен і яйця за типовим рецептом.
- Страви без жодного знайденого алергену: медальйон з телятини, овочі гриль, батат фрі, картопля фрі.
- Базовий сніданок: алергени білка на вибір гостя (лосось — риба, креветки — ракоподібні) не враховано.

Тепер алергени кожної страви перевіряє й виправляє адміністратор разом із кухнею в адмін-панелі:
«Позиції» → страва → «Алергени». Автоматичне визначення (`ALLERGEN_RULES` у `scripts/kitchen.mjs`)
потрібне лише для першого заповнення бази.

## Особливості даних і що варто перевірити

**Як працює квіз**
- Якщо для позиції немає відповіді (наприклад, країна пива невідома), це питання для неї не показується.
- Кухня: питання «Склад» і «Алергени» — чеклісти, треба позначити всі правильні варіанти.
  У «Складі» показуються **всі** інгредієнти страви + 4 неправильні з інших страв; варіанти,
  схожі на інгредієнти самої страви («Пармезан» для страви з «Сир пармезан»), не пропонуються.
  Фрази, що містять кілька інгредієнтів («начинка з фаршу тигрової креветки та курячого філе»),
  розкладаються на окремі інгредієнти в `PHRASE_SPLITS` у `scripts/kitchen.mjs`; скрипт збірки
  попередить, якщо з'явиться нова така фраза.
- «Алергени» — необов'язкове питання: його можна пропустити, а помилка в ньому не впливає на
  серію, точність і банк помилок (позначається жовтим «Не все — на результат не впливає»).
- Режими сторінки: «Каталог» і «Помилки» (дві кнопки під пошуком) та квіз. «Тренажер» посередині
  нижньої навігації (Вино · Бар · Тренажер · Коктейлі · Кухня) відкриває вибір тесту: тест поточного
  розділу стартує одразу, інший розділ відкривається одразу в режимі квізу (`bar.html#quiz`).
- Стартовий екран — каталог. Пошук і фільтри-чипи в шапці працюють з будь-якого режиму (перемикають
  на каталог). Картка позиції відкривається панеллю знизу (на комп’ютері — діалогом); закривається
  ✕, Esc, змахом вниз або кнопкою «Назад». Кнопка «Тренувати цю позицію» починає квіз з цієї
  позиції й далі продовжує по всьому меню.
- Для кухні картка показує орієнтовну пару з винної карти (`pairingProfile` у `item-sheet.js`) —
  це підказка за характером страви, а не рекомендація сомельє.
- Бар: країну прибрано з назв («ORA, Франція» → «ORA»), бо вона підказувала відповідь.
  У назвах Hoegaarden, Leffe Brune, Becherovka кириличні літери замінено на латинські (для пошуку).
- Кухня: у тренажері страви зі специфікації кухні (`data/source/residence_menu_full.json`).
  11 страв, яких у специфікації не було, додано в неї з ChoiceQR і позначено `"source": "choiceqr"`
  з поясненням у полі `note`: міні-піци (Б'янка, Лосось-шпинат, Пепероні), штрудель, карамельний
  чізкейк, вареники з горішками, соте з морепродуктами та розділ «Дітям». **Склад цих страв варто
  звірити з кухнею**: він узятий з короткого опису ChoiceQR, а для мітболів з пюре, сирничків і
  вершкових спагетті (в ChoiceQR без опису) — визначений за назвою та заготовками кухні.
- Хліб (пшеничний і житній тартін, гречані грінки) у тренажер не входить: у ChoiceQR для нього
  немає ні складу, ні фото.

**Відповіді, взяті не з меню (варто звірити з баром)**
- Склад класичних коктейлів, якого немає в описі меню: Porn Star Martini, Whiskey Sour,
  Pisco Sour, French 75, Aperol Spritz, а також Clover Club і Aperol Spritz б/а.
- Країни, не вказані в меню: Corona (Мексика), Stella Artois, Hoegaarden, Leffe (Бельгія),
  Tanduay (Філіппіни), Pisco (Чилі).
- Країна невідома, питання не показується: Botafogo Spiced/Black, Stirling, Milk Stout,
  Samurai's Daughter, Party Weizen, Zero Stress.

**Можливі опечатки в ChoiceQR (у тренажері лишено як у меню)**
PISCO CAPEI (ймовірно Capel), JANARA / JARANA, TANDAY (в описі — Tanduay), MAI THAI,
MARQUIS DE SAIN-LOUP (в описі — Saint-Loup). Після виправлення в ChoiceQR треба також оновити
ключ у таблиці `BAR` / `COCKTAILS` і перезапустити парсер та скрипт збірки.
